# reasoning_brain_storage

`reasoning_brain_storage/` is the storage-domain evolution of the original `reasoning-brain/` concept in Persistent Reasoning Light.

Persistent Reasoning remains the governing principle.

This directory is not a side utility and not a benchmark-only helper.
It is the domain that owns structured reasoning state.

The benchmark system is only one consumer of this storage layer.

---

## Purpose

`reasoning_brain_storage/` exists to manage reasoning brain state as a first-class persistent structure.

This includes:

- empty brain templates
- active benchmark/runtime brain state
- curated seeded brain state
- immutable snapshots
- experiment evolution lineages
- structured storage tools for brain lifecycle operations

The goal is to prevent ad hoc filesystem manipulation and make reasoning state transitions explicit, reproducible, and auditable.

---

## Architectural Principle

```text
Persistent Reasoning first.

benchmark = consumer
reasoning_brain_storage = owner of reasoning state
```

Benchmark code must not manipulate reasoning brain folders directly.

All structured brain operations must go through explicit storage tools.

## Semantic Meaning of Core Brain States

### `templates/empty/`
Canonical zero-state reasoning brain template.

This is the canonical empty starting point.

It defines the canonical v1 reasoning brain structure and should be used as the source for resets and cold starts.

`empty/` is a template/reference state, not an active evolving brain.

---

### `benchmarks/runtime/`
Mutable active reasoning brain.

This is the working brain used during accumulation-oriented benchmark runs or runtime-like experiments.

It may change across runs if the active profile allows accumulation.

`runtime/` is the only benchmark-facing brain state that is expected to mutate.

---

### `benchmarks/seeded/`
Curated frozen benchmark brain.

This is a controlled input state used when benchmark runs need a non-empty starting brain.

`seeded/` must not be mutated during benchmark execution.

It is intended as a stable, reviewed, reproducible reference state.

---

### `snapshots/`
Immutable captured brain states from specific runs.

Snapshots are point-in-time copies used for:
- audit
- comparison
- rollback
- lineage tracking
- later promotion or review
 
Snapshots must be treated as immutable.

### `compare_reports/`
Read-only structural comparison and inspection outputs.

These reports are generated by the storage-domain compare entry point:
`reasoning_brain_storage/run_brain_compare.py`

They are intended for:
- audit
- inspection
- structural comparison

They are not merge artifacts and do not imply snapshot input, branching, or lineage semantics.

---

### `evolution/<experiment_id>/`
Accumulation lineage for a specific experiment.

Each `run_n/` represents one step in an experiment’s brain evolution.

`plateau/` is the currently designated stabilization point for that lineage.

In v1, plateau may be marked manually.

## Benchmark Relationship

The benchmark system does not own reasoning state.

Instead:
- benchmark selects profile
- benchmark requests brain input/output behavior
- benchmark calls storage tools
- storage tools manage brain transitions

This keeps benchmark orchestration clean and prevents folder-level drift.

## Storage-Domain Compare Entry Point

Use:

```text
python reasoning_brain_storage/run_brain_compare.py inspect ...
python reasoning_brain_storage/run_brain_compare.py compare ...
```

This entry point is:
- storage-owned
- read-only
- structural

V1 comparison outputs are:
- `comparison_summary.json`
- `diff.json`
- `intersect.json`
- `diff.md`
- `intersect.md`

V1 meaning:
- `diff` = added / removed / mismatched structural differences
- `intersect` = shared persisted core under conservative identity rules

Important:
- `intersect` is not truth
- mismatch is structural same-id payload mismatch, not semantic contradiction
- union/merge semantics remain deferred

## Static vs Accumulative Behavior

“Static” is not a separate storage universe. It is a profile-controlled behavior.

The same storage domain may be used in:
- static mode
brain is read-only for the run

- accumulative mode
runtime brain may evolve across runs

This behavior is controlled by profile parameters, not by different ad hoc directory logic.

---

## Profile Integration

Profiles may define brain behavior using:

```
brain_mode: accumulative | static

brain_in:
  type: empty | runtime | seeded | snapshot
  ref: ...

brain_out:
  mode: continue | snapshot | empty
```

**Meaning**

### brain_mode

Defines whether the active run is allowed to evolve runtime brain state.

### brain_in

Defines the source brain state for the run.

Examples:
- start from empty template
- continue from runtime
- start from seeded snapshot
- branch from saved snapshot

### brain_out

Defines what happens to runtime brain after the run.

Supported meanings:
- `continue` → keep runtime brain as active state
- `snapshot` → capture immutable snapshot of the resulting brain
- `empty` → discard all runtime mutations and reset runtime brain to the canonical empty template after the run

### Additional constraints:
- reset must be explicit and complete
- no partial cleanup is allowed
- no artifacts from the previous run may remain
- lineage must not be implicitly preserved in runtime

Snapshots (if created before reset) remain unaffected.

## Minimal Expected Empty Brain Structure

The empty template is the canonical full v1 reasoning brain shape.

With a minimal valid context shape such as:

```
{
  "active_task": null,
  "constraints": [],
  "decisions": [],
  "open_issues": []
}
```

Full `empty/` directory structure map:

```
empty/

|  |- procedures/
|  `- issues/
|- runtime/
|  |- drafts/
|  `- inbox/
|- relations/
`- views/

Persisted accepted artifacts belong only under:

```

Canonical category mapping:
- task -> brain/tasks/
- decision -> brain/decisions/
- constraint -> brain/constraints/
- procedure -> brain/procedures/
- issue -> brain/issues/

## Storage Tools Rule (CRITICAL)

All structured brain manipulation logic must live under:

```
reasoning_brain_storage/tools/
```

Benchmark code must not:
- copy brain folders directly
- delete brain folders directly
- rebuild `working_context.json` manually
- write artifact files directly into brain folders
- perform ad hoc snapshotting
- mutate seeded brain

Benchmark code may only invoke explicit storage operations.

## Artifact Lifecycle (High-Level)

Target lifecycle:

```
model output
→ Artifact Suggestion
→ parse
→ acceptance check
→ if accepted → persist into runtime brain
→ rebuild working context
```

Important notes:
- raw free-form text must not be written directly into brain
- duplicates must not be blindly appended
- rediscovery should be handled explicitly
- acceptance and persistence must be structured and auditable
- accepted persisted artifacts belong only under `brain/<plural-category>/`

---

## Artifact Acceptance Ownership

Artifact acceptance is not benchmark logic.

### Rules:
- Benchmark layer may only produce artifact candidates.
- Benchmark must not decide whether an artifact is accepted.
- Storage layer is responsible for structured persistence only.
- This storage layer assumes acceptance has already happened upstream.
- Storage exports the governance-facing read-only `brain_state` snapshot.

Minimal v1 governance-facing `brain_state` shape:

```
{
  "artifacts_by_id": {
    "<artifact_id>": {
      ...full persisted artifact payload...
    }
  }
}
```

Seam rules:
- export reads only canonical persisted artifacts under `brain/<plural-category>/`
- export is deterministic and side-effect free
- export excludes `runtime/drafts`, `runtime/inbox`, `relations`, and live storage handles
- malformed persisted artifacts raise explicit storage validation errors
- duplicate persisted artifact ids raise explicit storage conflict errors

---

## No Silent Mutation Rule

This storage layer must preserve strict mutation discipline.

Forbidden behavior includes:
- silent overwrite
- implicit merge
- hidden cleanup
- in-place mutation without explicit operation
- mutation during read-only operations

All brain changes must be explicit.

---

## Append-Only Mutation Discipline

Reasoning brain evolution follows an append-oriented model.

### Rules:

- Existing artifacts must not be modified in place.
- New knowledge must be introduced via new artifacts.
- Replacement must be explicit and traceable.
- Silent mutation of existing artifacts is forbidden.

### Implications:

- History must remain reconstructable.
- Brain evolution must be auditable.
- No hidden rewriting of reasoning state is allowed.

This preserves the integrity of reasoning lineage.

## Brain Diff Auditor

A dedicated structured comparison tool belongs in:

```
reasoning_brain_storage/tools/
```

Its purpose is to compare two or more brains and report:
- added artifacts
- removed artifacts
- duplicate candidates
- contradiction candidates
- working-context changes
- structural growth across runs

This is the storage-domain equivalent of diff analysis for reasoning structures.

## Why This Exists

Without a dedicated reasoning brain storage domain, benchmark and runtime code tend to manipulate folders ad hoc.

That leads to:
- drift in state semantics
- implicit mutations
- weak reproducibility
- unclear lineage
- benchmark/storage ownership confusion

`reasoning_brain_storage/` exists to stop that drift and make reasoning state explicit.
